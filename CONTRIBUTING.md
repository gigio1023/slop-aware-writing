# Contributing

This repository publishes two independently installable skills. Changes are small and frequent. The commit log is the durable decision record for why a change was made, what it rejected, and what was checked before it shipped. Source provenance, inspection dates, and reuse status live in the [source register](docs/sources-and-inspiration.md). The rules below keep the decision history readable a year later.

## Markdown source layout

Keep each natural prose paragraph on one source line, including paragraphs within list items, blockquotes, and Markdown templates. Use editor soft wrapping for display; do not manually wrap prose to 80, 100, or any other column width. Preserve paragraph boundaries, list structure, tables, fenced code, HTML, intentional hard breaks, frontmatter semantics, and literal examples. In fenced Markdown templates, unwrap only prose whose layout is not part of the example. Code and docstring line-length rules are outside this convention.

## Commit Boundaries

A commit is one coherent decision that can be reviewed and reverted on its own. Keep a rule change together with the reference file, README line, and design note that make it correct. Split unrelated domains — a skill-behavior change and a packaging change do not belong in the same commit merely because both were in the working tree. Never sweep a dirty tree into one catch-all commit; stage explicit paths and leave unrelated work alone.

## Subject

Use the repository's Conventional Commits prefix, then an imperative summary of the outcome.

```text
fix(references): condition C-8 by genre, cover impersonal registers
```

- Prefixes in use: `feat`, `fix`, `docs`, `refactor`, `chore`. Scope is optional and names the affected area (`skill`, `references`, `docs`).
- At most 72 characters, no trailing period.
- Describe what is now true, not the editing activity. "Add a keep test to C-8" beats "update korean-tells.md".

## Body

**A detailed body is mandatory for every commit**, including documentation-only ones. A reader with no access to this conversation, the working tree, or any issue tracker must be able to reconstruct the intent, the reasoning, the outcome, and the evidence from the log alone. Prefer useful detail over brevity, but do not list files the diff already shows.

Use these four sections:

```text
Context:
- Why the work was needed: the failure, request, or gap that prompted it
- Evidence behind the decision, and constraints that bounded it

Changes:
- What changed and how, including the judgment calls
- What was deliberately rejected, and on what grounds

Results:
- What behaves differently now, for the skill or its reader
- Remaining limits, risks, or follow-up work

Validation:
- Exact commands or checks run, and what they reported
- Write "Not run" with a reason when no check applies
```

Rules that are specific to this repository:

- **Cite the evidence type for any rule change.** A rule carries a measured AI-vs-human discriminator, Korean style evidence, an observation, or house style. Say which, and name the source or study when one exists.
- **Record rejections.** When an upstream idea or an obvious fix was considered and dropped, the body says so and why. A later reader will otherwise re-propose it.
- **State what was not verified.** Synthetic checks and real-document checks carry different weight; do not let a passing validator imply behavioral evidence it cannot give.
- Do not add agent branding, "generated by" notes, or synthetic co-author trailers.

## Before Pushing

Run the checks that the change actually touches, and report their results in the body:

```bash
npx --yes skills add . --list --full-depth
```

The command must report exactly `slop-aware-writing` and `korean-clarity`. Also confirm that every referenced path exists, that each `SKILL.md` frontmatter name matches its folder, and that `README.md` and `README.ko.md` stay aligned. Push to `main`; pull requests are reserved for changes worth a review checkpoint, and history on `main` is not rewritten once others may have pulled it.
